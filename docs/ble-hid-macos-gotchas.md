# BLE-HID на macOS: грабли, на которые мы уже наступали

Заметки для следующего этапа — приложения на маке. Про баги прошивки и
библиотеки написано отдельно, в
`../firmware/libs/ESP32_BLE_Keyboard/KEYDECK-PATCH.md`; здесь только то, что
касается стороны macOS и отладки связки.

## Что чем смотреть

```sh
# Главный признак, что macOS реально завёл клавиатуру: HID-устройство с нашим VID.
# VID у прошивки 0x303A (Espressif), но PnP ID отдаётся big-endian, поэтому
# в системе он виден как 0x3A30 — грепать надо по нему.
hidutil list | grep -i 0x3a30
#   ожидаем: IOHIDUserDevice + AppleUserHIDEventDriver, продукт "keydeck"

# Что система думает про спаривание, шифрование и GATT
log show --last 5m --predicate 'process == "bluetoothd"' --style compact \
  | grep -iE "Encryption is now enabled|Pairing completed|Read Not Permitted|HID"

# Состояние устройства. Строка "Services: < BLE >" = подключено.
system_profiler SPBluetoothDataType | grep -A 7 -i keydeck
```

Ключевой признак поломки: устройство в Bluetooth «Connected» и `Minor Type:
Keyboard`, но HID-устройства в `hidutil list` **нет**. Значит HOGP-сетап не
дошёл до конца, и нажатия никуда не пойдут — смотреть лог `bluetoothd`.

## Тупики, в которые не надо возвращаться

**`CoreBluetooth` из CLI не видит HID-сервис.** macOS скрывает сервис `0x1812` от
приложений, пока устройство не спарено: `discoverServices(nil)` возвращает только
`180A` и `180F`, а `discoverServices([1812])` — пустой список, хотя системный стек
(`bluetoothd`) этот сервис прекрасно видит и читает. Проверять HID-профиль из
своего BLE-центра бессмысленно, только через системное спаривание.

**`blueutil` не спарит BLE-устройство.** Он работает через IOBluetooth, то есть
только с классическим Bluetooth: в `blueutil --paired` keydeck не появляется
вообще, `--connect` возвращает `Failed to connect`. Ставили его зря.

**`CGEventTap` не создаётся без разрешения Accessibility.** Тестовый перехватчик
падал с `FAILED to create event tap`, пока не выдали Accessibility/Input
Monitoring. Это ровно то же ограничение, в которое упрётся будущее приложение —
в `macos/README.md` оно уже учтено как обязательное разрешение.

**Окно подтверждения спаривания может перехватить браузер.** В логе было:
`Displaying pairing request alert ... on behalf of session
"ru.yandex.desktop.yandex-browser"`. Chromium-браузеры регистрируют себя агентом
спаривания (Web Bluetooth), и если диалог достался им, спаривание молча не
завершается: `Encryption is now disabled`, `paired, BLE, 0 total`. Лечится
закрытием браузера перед спариванием.

## Порядок событий, который важно понимать

1. Соединение устанавливается **до** шифрования. macOS сразу начинает читать
   GATT, и если характеристика помечена `READ_ENCRYPTED`, чтение вернёт
   `Read Not Permitted` (ATT `0x02`), а не «нет шифрования».
2. Шифрование поднимается уже после подтверждения спаривания — с задержкой в
   несколько секунд. При наличии бонда оно включается сразу после коннекта.
3. Если HOGP-сетап сорвался, macOS **не переигрывает его сам**: помогает только
   заставить систему считать устройство новым (см. ниже).

## macOS кэширует Report Map

Report Map и HID-дескриптор мак запоминает при спаривании. После правки дескриптора
(например, потолка кодов `0x65` → `0x73`) перепрошивки недостаточно: мак
продолжает пользоваться старым закэшированным дескриптором. Нужно, чтобы он счёл
устройство новым:

1. «Убрать устройство» (`Forget`) в Системных настройках → Bluetooth;
2. стереть бонд и на стороне платы: `esptool erase-flash` + перепрошивка (иначе в
   NVS останется старый ключ);
3. спарить заново.

Смена VID/PID в прошивке тоже заставляет мак перечитать дескриптор — этим и
воспользовались, уйдя с дефолтного Apple-VID `0x05AC` на `0x303A`.

## Коды клавиш для приложения

Нажатия приходят как F13..F20. Виртуальные коды macOS (`keycode` в `CGEvent`),
они не совпадают с HID usage:

| Кнопка | HID usage | macOS keycode |
|---|---|---|
| F13 | 0x68 (104) | 105 |
| F14 | 0x69 (105) | 107 |
| F15 | 0x6A (106) | 113 |
| F16 | 0x6B (107) | 106 |
| F17 | 0x6C (108) | 64 |
| F18 | 0x6D (109) | 79 |
| F19 | 0x6E (110) | 80 |
| F20 | 0x6F (111) | 90 |

## Плата на USB

Определяется как `Espressif USB JTAG_serial debug unit`. Прошивка идёт через
нативный USB-Serial-JTAG, поэтому обязательны `USB Mode: Hardware CDC and JTAG` и
`USB CDC On Boot: Enabled` — иначе молчит `Serial`.

Если прошивка ушла в цикл перезагрузки (паника по `LoadProhibited`), `esptool` не
успевает поймать чип: `Failed to connect ... No serial data received`. Помогает
физическое передёргивание USB, после которого надо шить сразу.
